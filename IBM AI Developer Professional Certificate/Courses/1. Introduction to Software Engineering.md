## Software Development Life Cycle (SDLC)

### Definition
- The **SDLC** is a systematic process used to develop **high-quality software** within a **predictable timeframe and budget**.
- It ensures the software meets **client business requirements** through phases like **planning**, **design**, and **development**.

### History
- Originated in the **mid-1960s** due to the increasing complexity of software.
- Early model: **Waterfall method** – a linear approach with distinct, sequential stages.
- Later adapted to **iterative models** to better handle changing requirements.

### Purpose & Importance
- Minimizes **risks** and **costs** during software development.
- Provides a **structured roadmap** rather than an ad hoc approach.



## Phases of the Software Development Life Cycle (SDLC)

The SDLC typically consists of **six discrete phases**, which may include iteration to accommodate changing requirements.


### 1. Planning
**Main Goal:** Gather and analyze **requirements**.

**Key Tasks:**
- Identify users, inputs/outputs, compliance needs, risks, and resources.
- Estimate costs and create a **project schedule**.
- Assign roles to team members.
- Create **prototypes** to clarify unclear requirements.
- **Output:** Software Requirements Specification (**SRS**) document.



### 2. Design
**Main Goal:** Define system **architecture** based on the SRS.

**Key Tasks:**
- Collaborate to design system structure.
- Create **prototypes** for feedback if necessary.
- **Output:** **Design document** for developers.



### 3. Development
**Main Goal:** **Code** the software based on the design document.

**Key Tasks:**
- Assign and implement coding tasks.
- Use appropriate languages, tools, and follow organization standards.



### 4. Testing
**Main Goal:** Ensure software is **stable, secure, and meets requirements**.

**Key Tasks:**
- Conduct various testing levels: unit, integration, system, and acceptance.
- Identify and fix bugs.
- Use **manual, automated, or hybrid** testing methods.



### 5. Deployment
**Main Goal:** Release software to the **production environment**.

**Key Tasks:**
- Deploy in stages (e.g., UAT → Production).
- Make software available via website, app store, or internal distribution.



### 6. Maintenance
**Main Goal:** Address **bugs**, UI issues, and new requirements post-deployment.

**Key Tasks:**
- Collect user and stakeholder feedback.
- Apply critical fixes or enhancements.
- Restart SDLC if major updates are needed.

## Building Quality Software

This lesson covers **six key software engineering processes** used to build high-quality software:


### 1. Requirements Gathering
- Collect and document what the software must do.
- **Output:** Software Requirements Specification (**SRS**)
- **Types of Requirements:**
  - Functional
  - UI / External
  - System Features
  - Non-Functional


### 2. Design
- Transform requirements into a system structure that can be coded.
- **Includes:**
  - Components with defined behaviors and interactions
  - Architecture, performance, security, and platform considerations
  - Business rules, API design, user interface (UI), and database design


### 3. Coding for Quality
- Code should be:
  - Clean, readable, maintainable, secure, and efficient
- **Best Practices:**
  - Follow coding standards, conventions, and styles
  - Use automated tools like **linters**
  - Add meaningful **comments** in code


### 4. Testing
- Ensure the software meets requirements and is **free of bugs**
- **Testing Levels:**
  - Unit
  - Integration
  - System
  - User Acceptance (UAT)
- **Testing Types:**
  - Functional
  - Non-Functional
  - Regression
- **Methods:** Manual, Automated, or Hybrid


### 5. Releases
- **Alpha Release:** Early internal version (may contain bugs)
- **Beta Release:** Limited external release for feedback and testing
- **GA (General Availability):** Final stable release for all users


### 6. Documenting
- **System Documentation** (for technical users):
  - README files, inline comments, architecture/design docs, maintenance guides
- **User Documentation** (for end users):
  - User guides, help manuals, instructional videos, inline help


## Requirements Gathering & Specification Documents
### 1. Requirement Gathering (6-Step Process)

- **Identify Stakeholders**  
  Anyone impacted by the system (users, admins, engineers, etc.).

- **Establish Goals and Objectives**  
  - *Goals*: Broad, long-term aims.  
  - *Objectives*: Specific, measurable steps.

- **Elicit Requirements**  
  Conduct interviews, surveys, and use case discussions.

- **Document Requirements**  
  Organize and write down clearly; relate back to goals.

- **Analyze & Confirm**  
  Ensure consistency and clarity; confirm with stakeholders.

- **Prioritize Requirements**  
  Rank based on importance — must-have, desired, optional.


### 2. Types of Specification Documents

#### SRS (Software Requirements Specification)

- Describes what the software should do.
- Includes purpose, scope, functional and non-functional requirements, system features, constraints, and assumptions.

#### URS (User Requirements Specification)

- Focuses on what users need and why.
- Written from the end-user’s point of view using user stories or use cases.
- Basis for User Acceptance Testing (UAT).

#### SysRS (System Requirements Specification)

- Covers entire system-level requirements, not just software.
- Includes system capabilities, hardware/software interfaces, regulations, policies, user profiles, performance and security expectations, and acceptance criteria.


### 3. Key Differences Between SRS, URS, and SysRS

- **URS**: What the user needs — simple, use-case focused.
- **SRS**: What the software must do — technical, focused on software functionality.
- **SysRS**: Entire system expectations — covers software, hardware, users, environment, and more.

## Software Development Methodologies

### Waterfall Model
- **Nature**: Sequential – each phase must finish before the next begins.  
- **Pros**:  
  - Easy to understand and follow.  
  - Well-defined stages and roles.  
  - Easier to estimate budget/resources (since planning is upfront).  
- **Cons**:  
  - Inflexible – difficult to handle changes once the project is underway.  
  - Customer sees the product late (often during testing).  
  - Long release cycles.  

### V-Shape Model
- **Nature**: Sequential, like Waterfall, but shaped as a “V”.  
  - Left side: Verification (planning → system design → architecture design → module design).  
  - Bottom: Coding.  
  - Right side: Validation (unit testing → integration testing → system testing → acceptance testing).  
- **Pros**:  
  - Simple and structured.  
  - Test plans are created early, saving time later.  
- **Cons**:  
  - Even more rigid than Waterfall.  
  - Hard to adapt to changing requirements once testing starts.  

### Agile Model
- **Nature**: Iterative and cyclical, based on short cycles (“sprints” of 1–4 weeks).  
- **Process**:  
  - Each sprint includes planning, coding, testing, and feedback.  
  - Produces small chunks of working code → demoed to stakeholders for feedback.  
  - Builds toward an MVP (minimum viable product).  
- **Core Values (Agile Manifesto)**:  
  - Individuals & interactions > processes & tools.  
  - Working software > documentation.  
  - Customer collaboration > contract negotiation.  
  - Responding to change > following a plan.  
- **Pros**:  
  - Flexible, quickly adapts to changes.  
  - Continuous feedback improves alignment with user needs.  
  - Supports modular, incremental development.  
- **Cons**:  
  - Harder to plan budgets/schedules upfront.  
  - Overall scope is less clearly defined.  

### Key Comparison
- **Waterfall & V-Shape** → Sequential, rigid, good for stable requirements, easy to plan.  
- **Agile** → Iterative, flexible, customer-focused, better for evolving requirements, but harder to budget.
