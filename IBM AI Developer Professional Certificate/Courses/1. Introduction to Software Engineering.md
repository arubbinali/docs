## 1. Software Development Life Cycle (SDLC)

### Definition
- The **SDLC** is a systematic process used to develop **high-quality software** within a **predictable timeframe and budget**.
- It ensures the software meets **client business requirements** through phases like **planning**, **design**, and **development**.

### History
- Originated in the **mid-1960s** due to the increasing complexity of software.
- Early model: **Waterfall method** – a linear approach with distinct, sequential stages.
- Later adapted to **iterative models** to better handle changing requirements.

### Purpose & Importance
- Minimizes **risks** and **costs** during software development.
- Provides a **structured roadmap** rather than an ad hoc approach.



## 2. Phases of the Software Development Life Cycle (SDLC)

The SDLC typically consists of **six discrete phases**, which may include iteration to accommodate changing requirements.


### 1. Planning
**Main Goal:** Gather and analyze **requirements**.

**Key Tasks:**
- Identify users, inputs/outputs, compliance needs, risks, and resources.
- Estimate costs and create a **project schedule**.
- Assign roles to team members.
- Create **prototypes** to clarify unclear requirements.
- **Output:** Software Requirements Specification (**SRS**) document.



### 2. Design
**Main Goal:** Define system **architecture** based on the SRS.

**Key Tasks:**
- Collaborate to design system structure.
- Create **prototypes** for feedback if necessary.
- **Output:** **Design document** for developers.



### 3. Development
**Main Goal:** **Code** the software based on the design document.

**Key Tasks:**
- Assign and implement coding tasks.
- Use appropriate languages, tools, and follow organization standards.



### 4. Testing
**Main Goal:** Ensure software is **stable, secure, and meets requirements**.

**Key Tasks:**
- Conduct various testing levels: unit, integration, system, and acceptance.
- Identify and fix bugs.
- Use **manual, automated, or hybrid** testing methods.



### 5. Deployment
**Main Goal:** Release software to the **production environment**.

**Key Tasks:**
- Deploy in stages (e.g., UAT → Production).
- Make software available via website, app store, or internal distribution.



### 6. Maintenance
**Main Goal:** Address **bugs**, UI issues, and new requirements post-deployment.

**Key Tasks:**
- Collect user and stakeholder feedback.
- Apply critical fixes or enhancements.
- Restart SDLC if major updates are needed.

## 3. Building Quality Software

This lesson covers **six key software engineering processes** used to build high-quality software:


### 1. Requirements Gathering
- Collect and document what the software must do.
- **Output:** Software Requirements Specification (**SRS**)
- **Types of Requirements:**
  - Functional
  - UI / External
  - System Features

### 2. Design
- Transform requirements into a system structure that can be coded.
- **Includes:**
  - Components with defined behaviors and interactions
  - Architecture, performance, security, and platform considerations
  - Business rules, API design, user interface (UI), and database design


### 3. Coding for Quality
- Code should be:
  - Clean, readable, maintainable, secure, and efficient
- **Best Practices:**
  - Follow coding standards, conventions, and styles
  - Use automated tools like **linters**
  - Add meaningful **comments** in code


### 4. Testing
- Ensure the software meets requirements and is **free of bugs**
- **Testing Levels:**
  - Unit
  - Integration
  - System
  - User Acceptance (UAT)
- **Testing Types:**
  - Functional
  - Non-Functional
  - Regression
- **Methods:** Manual, Automated, or Hybrid


### 5. Releases
- **Alpha Release:** Early internal version (may contain bugs)
- **Beta Release:** Limited external release for feedback and testing
- **GA (General Availability):** Final stable release for all users


### 6. Documenting

  - README files, inline comments, architecture/design docs, maintenance guides
- **User Documentation** (for end users):
  - User guides, help manuals, instructional videos, inline help


## 4. Requirements Gathering & Specification Documents
### 1. Requirement Gathering (6-Step Process)

- **Identify Stakeholders**  
  Anyone impacted by the system (users, admins, engineers, etc.).

- **Establish Goals and Objectives**  
  - *Goals*: Broad, long-term aims.  
  - *Objectives*: Specific, measurable steps.

- **Elicit Requirements**  
  Conduct interviews, surveys, and use case discussions.

- **Document Requirements**  
  Organize and write down clearly; relate back to goals.

- **Analyze & Confirm**  
  Ensure consistency and clarity; confirm with stakeholders.

- **Prioritize Requirements**  
  Rank based on importance — must-have, desired, optional.


### 2. Types of Specification Documents

#### SRS (Software Requirements Specification)

- Describes what the software should do.
- Includes purpose, scope, functional and non-functional requirements, system features, constraints, and assumptions.

#### URS (User Requirements Specification)

- Focuses on what users need and why.
- Written from the end-user’s point of view using user stories or use cases.
- Basis for User Acceptance Testing (UAT).

#### SysRS (System Requirements Specification)

- Covers entire system-level requirements, not just software.
- Includes system capabilities, hardware/software interfaces, regulations, policies, user profiles, performance and security expectations, and acceptance criteria.


### 3. Key Differences Between SRS, URS, and SysRS

- **URS**: What the user needs — simple, use-case focused.
- **SRS**: What the software must do — technical, focused on software functionality.
- **SysRS**: Entire system expectations — covers software, hardware, users, environment, and more.

## 5. Software Development Methodologies

### Waterfall Model
- **Nature**: Sequential – each phase must finish before the next begins.  
- **Pros**:  
  - Easy to understand and follow.  
  - Well-defined stages and roles.  
  - Easier to estimate budget/resources (since planning is upfront).  
- **Cons**:  
  - Inflexible – difficult to handle changes once the project is underway.  
  - Customer sees the product late (often during testing).  
  - Long release cycles.  

### V-Shape Model
- **Nature**: Sequential, like Waterfall, but shaped as a “V”.  
  - Left side: Verification (planning → system design → architecture design → module design).  
  - Bottom: Coding.  
  - Right side: Validation (unit testing → integration testing → system testing → acceptance testing).  
- **Pros**:  
  - Simple and structured.  
  - Test plans are created early, saving time later.  
- **Cons**:  
  - Even more rigid than Waterfall.  
  - Hard to adapt to changing requirements once testing starts.  

### Agile Model
- **Nature**: Iterative and cyclical, based on short cycles (“sprints” of 1–4 weeks).  
- **Process**:  
  - Each sprint includes planning, coding, testing, and feedback.  
  - Produces small chunks of working code → demoed to stakeholders for feedback.  
  - Builds toward an MVP (minimum viable product).  
- **Core Values (Agile Manifesto)**:  
  - Individuals & interactions > processes & tools.  
  - Working software > documentation.  
  - Customer collaboration > contract negotiation.  
  - Responding to change > following a plan.  
- **Pros**:  
  - Flexible, quickly adapts to changes.  
  - Continuous feedback improves alignment with user needs.  
  - Supports modular, incremental development.  
- **Cons**:  
  - Harder to plan budgets/schedules upfront.  
  - Overall scope is less clearly defined.  

### Key Comparison
- **Waterfall & V-Shape** → Sequential, rigid, good for stable requirements, easy to plan.  
- **Agile** → Iterative, flexible, customer-focused, better for evolving requirements, but harder to budget.


## 6. Software Versions

### Introduction
Software versions tell us a lot about programs and applications.  
Users can determine what software version they are using, and developers can provide useful information with version numbers.  

Software version numbers vary in length and meaning; however, most version numbers follow a similar format and represent similar information.  
Version numbers indicate when the software was released, when it was updated, and if any minor changes or patches were made to the software.  
Software versioning is how developers keep track of new software, updates, and patches.


### Version Numbers
- Version numbers can be displayed in several ways.  
- They can be short or long, depending on the software and developer preference, with 2, 3, or 4 number sets.  
- Each number set is divided by a period.  

Examples:
- **1.0** → first release with no updates, patches, or fixes.  
- **0.9** → beta or testing version.  
- Longer versions may have 4 sets of numbers.  
- Some developers use **dates** for versioning.  
  - Example: **Ubuntu Linux 18.04.2** → released in April 2018.

### Semantic Numbering System
Some version numbers follow the semantic numbering system and have 4 parts separated by a period:

1. **First number** → Major changes (new release).  
2. **Second number** → Minor changes.  
3. **Third number** → Patches or minor bug fixes.  
4. **Fourth number** → Build number or build date (less significant changes).  

### Finding Software Versions
- Software version numbers are identified in the **About** or **Help** section.  
- Example (Google Chrome desktop):  
  1. Select the three dots in the top-right corner.  
  2. Select **Help**.  
  3. Select **About** to view the version.  
  4. The browser version number will display.


### Compatibility
- Compatibility between old and new software versions is a common problem.  
- Updating to a newer version often resolves compatibility issues.  
- Some software is **backwards compatible**, meaning older files, programs, and systems still work with newer versions.

### Summary
- Version numbers show the history of changes, updates, and patches.  
- Some follow the semantic numbering system with 4 parts.  
- Compatibility between versions can be an issue.  
- Viewing your software version helps determine compatibility.


## 7. Software Testing

### Introduction
Software Testing is the practice of integrating quality checks throughout the software development cycle.  
The purpose of testing is to check whether the software matches expected requirements and ensure error-free software.  

In order to test software, the team writes **test cases**.  
- Test cases are written to verify the functionality of a software application and ensure requirements have been satisfied.  
- They can be written in different stages of the SDLC.  
- They may vary depending on the type of test or development method (e.g., Agile or Waterfall).


### Test Cases
A test case contains:  
- Steps  
- Inputs  
- Data  
- Expected outputs  

Regardless of the test type or development method, test cases should be written **after requirements are finalized**.  

Software testing helps evaluate whether the software product meets requirements and is error-free.  


### Categories of Testing
There are three broad categories of testing:  

1. **Functional Testing**  
   - Usually involves black-box testing (testing without looking at source code or internal structure).  
   - Concerned only with inputs and corresponding outputs of the System Under Test (SUT).  
   - Based entirely on testing functional requirements.  
   - Can be performed manually or using automated tools.  
   - Ensures the application is usable and accessible.  
   - Ensures user errors and edge cases are handled properly with appropriate error messages.  

2. **Non-Functional Testing**  
   - Tests attributes like performance, security, scalability, and availability.  
   - Checks whether the SUT’s non-functional behavior is correct.  
   - Answers questions such as:  
     - How does the application behave under stress?  
     - What happens when many users log in simultaneously?  
     - Are documentation instructions consistent with application behavior?  
     - Does it behave similarly on different operating systems?  
     - How does it handle disaster recovery?  
     - How secure is the application?  

3. **Regression Testing** (also called Maintenance Testing)  
   - Confirms that recent changes (e.g., bug fixes) do not negatively affect existing functionality.  
   - Should occur when requirements change or defects have been fixed.  
   - Requires selecting all or some test cases to re-run.  
   - Selection and prioritization can be challenging and depend on several factors.  
   - Common reasons for regression test case selection:  
     - Cases with frequent defects  
     - Frequently used functionality  
     - Recently changed features  
     - Complex or edge test cases  
     - Test cases with inconsistent results (randomly successful/failed)  


### Testing Levels
There are **four testing levels**, each occurring at different times in the SDLC to reduce overlap:  

1. **Unit Testing**  
   - Verifies the functionality of a specific section of code (usually at the function level).  
   - Performed by developers during the development phase.  
   - Aims to eliminate construction errors before integration.  
   - Increases both software quality and overall development efficiency.  

2. **Integration Testing**  
   - Identifies errors when two or more independent modules are combined.  
   - Another form of black-box testing.  
   - Conducted after unit-tested modules are integrated into the larger application.  
   - Exposes bugs that occur when modules interact with each other, databases, or external hardware.  
   - Uncovers issues like poor exception handling or requirement changes during module development.  

3. **System Testing**  
   - Conducted after integration testing on a complete, integrated system.  
   - Evaluates system compliance with specified requirements.  
   - Validates the system as a fully completed product.  
   - Includes both functional and non-functional testing.  
   - Performed in a **staging environment** that should be similar to production.  

4. **Acceptance Testing**  
   - Formal testing with respect to user needs, requirements, and business processes.  
   - Determines whether the system satisfies users, customers, and stakeholders.  
   - Usually conducted by the customer or stakeholders during the maintenance stage of the SDLC.  


### Summary
- There are **three categories of testing**: Functional, Non-Functional, and Regression.  
- **Unit Testing** verifies small, independent code chunks.  
- **Integration Testing** looks for errors when combining code modules.  
- **System Testing** validates the complete software system.  
- **Acceptance Testing** ensures user and business requirements are correctly implemented.  


## 8. Software Documentation

### Introduction
Software documentation is information about the software that describes what the product is and how to use it.  
These can be written, video, or graphical assets associated with a software product’s development and use.  

### Documentation Formats
- Documentation can be in **three formats**:  
  1. Written  
  2. Video  
  3. Graphical  

- Documentation is essential in all phases of the SDLC.  
- It can be written for different audiences such as:  
  - End users  
  - Software developers  
  - QA engineers  
  - System administrators  
  - Other stakeholders  


### Product vs. Process Documentation
- **Product Documentation** → Relates to the product’s functionality.  
- **Process Documentation** → Describes how to complete a task.  
  - Provides requirements for the quality implementation of a business process.  


### Categories and Types of Documentation
There are five main categories of documentation:  

1. **Requirements Documentation**  
   - Written during the planning phase of the SDLC.  
   - Intended for developers, architects, and QA personnel.  
   - Describes expected features and functionality.  
   - Includes:  
     - Software requirements specifications  
     - System requirements specifications  
     - User acceptance specifications  

2. **Design Documentation**  
   - Written by software architects and the development team.  
   - Explains how the software will be built to meet requirements.  
   - Includes both conceptual and technical design documents.  

3. **Technical Documentation**  
   - Includes code comments to help other developers understand behavior.  
   - May include working papers explaining code.  
   - Records engineers’ ideas and thoughts during project implementation.  

4. **Quality Assurance Documentation**  
   - Pertains to a testing team’s strategy, progress, and metrics.  
   - Types include:  
     - Test plans  
     - Test data  
     - Test scenarios  
     - Test cases  
     - Test strategies  
     - Traceability matrices (mapping test cases to requirements)  

5. **User Documentation**  
   - Intended for end-users.  
   - Explains how to operate, install, or troubleshoot software.  
   - Examples:  
     - FAQs  
     - Installation guides  
     - Help guides  
     - Tutorials  
     - User manuals  


### Standard Operating Procedures (SOPs)
- SOPs often accompany process documentation.  
- Process documentation provides an overview, while SOPs go into greater detail.  
- SOPs explain step-by-step how to accomplish common but complex tasks that are **organization-specific**.  
- Example: Checking in code may be common knowledge, but merging into a main branch may require organization-specific steps.  
- SOPs can be presented as:  
  - Flowcharts  
  - Hierarchical outlines  
  - Step-by-step instructions  


### Maintaining Documentation
- Documentation must be kept up to date.  
- Example: If a cloud-based application UI changes, its online manual must be updated.  
- Updating documentation usually happens during the **maintenance phase** of the SDLC.  
- Documentation should also be reviewed periodically to ensure accuracy.  

### Summary
- Documentation comes in three formats: **written, video, graphical**.  
- **Process documentation** → describes how to complete a task.  
- **Product documentation** → relates to how a product functions.  
- Types of product documentation include:  
  - Requirements  
  - Design  
  - Technical  
  - QA  
  - User  
- **SOPs** are written instructions that detail organization-specific procedures.

# Module 2 - Introduction to Software Development

## 1. Overview of Web and Cloud Development

- **Web Browsing Basics**
  - User enters a URL (e.g., `www.ibm.com`) in a browser (Chrome, Edge, Firefox, Safari).  
  - Browser contacts the server and requests website data.  
  - Server responds with:
    - **HTML** → structure of the page  
    - **CSS** → styling and design  
    - **JavaScript** → interactivity and dynamic content  

- **Static vs Dynamic Content**
  - **Static**: pre-stored on server.  
  - **Dynamic**: generated at request, often using databases.  
  - Most sites mix both for best user experience.  

- **Cloud Applications**
  - Similar to websites but rely on cloud-based infrastructure, storage, processing, and services.  
  - Advantages: **scalable** and **resilient**.  

- **Development Environments**
  - **Front-end**: client-side (HTML, CSS, JS, frameworks, tools).  
  - **Back-end**: server-side logic, authentication, database handling.  
  - **Full-stack**: both front-end and back-end.  

- **Developer Tools**
  - **Code editors**: Sublime Text, Atom, Vim, VS Code.  
  - **IDEs**: Visual Studio, Eclipse, NetBeans.  
  - IDEs add features: integration, building, compiling, debugging, Git/GitHub support, extensions, themes.  


### Key Takeaways
- Websites = communication between client and server.  
- Front-end = user interface; Back-end = server logic.  
- Full-stack = both.  
- IDEs/code editors help manage and build code efficiently.  


## 2. Learning Front-End Development

- **Front-end** = what the user interacts with (e.g., online shopping sites).  
- Built using **HTML, CSS, JavaScript** (work together).  

### Core Technologies
- **HTML** → structure (text, links, images, buttons, layout).  
- **CSS** → style (colors, fonts, layouts, cross-browser/device compatibility).  
- **JavaScript (JS)** → interactivity & dynamic behavior (e.g., login button functionality).  

### CSS Extensions
- **SASS (Syntactically Awesome Style Sheets)**  
  - Extension of CSS, backwards compatible.  
  - Adds variables, nesting, imports → faster, organized styling.  
- **LESS (Leaner Style Sheets)**  
  - Enhances CSS, backwards compatible.  
  - Uses `less.js` to convert to CSS.  

### Design Approaches
- **Adaptive design** → fixed layouts for specific devices (PC, mobile, tablet).  
- **Responsive design** → automatically resizes to any screen/device.  

### JavaScript Frameworks/Libraries
- **Angular (Google)** → full framework, fast rendering, routing, form validation.  
- **React.js (Facebook)** → JS library for building UI components; needs add-ons for routing.  
- **Vue.js (community)** → focuses on UI layer, flexible, scalable, works as both library & framework.  

### Key Points
- Front-end developers must **keep up with evolving tech**.  
- Websites should work across **browsers, OSs, and devices**.  

## 3. The Importance of Back-End Development

- Front-end → creates what user sees (HTML, CSS, JS).  
- Back-end → manages resources, processes requests, supplies data, ensures security.  
- Front-end & Back-end developers must collaborate closely.  

- Back-end tasks during browsing/shopping online:  
  - Handle login, searches, payment info.  
  - Process & maintain application logic.  
  - Retrieve product data from databases.  
  - Manage restricted areas (authentication & authorization).  
  - Secure handling of sensitive info (address, credit card).  

- Requests from front-end → handled by:  
  - **APIs** → work with data (JSON, XML).  
  - **Routes** → paths that take input & show results.  
  - **Endpoints** → defined targets for requests.  
  - Missing endpoint → server returns 404 error.  

- Back-end developer skills:  
  - At least one back-end language & frameworks.  
  - **JavaScript** → Node.js, Express.  
  - **Python** → Django, Flask.  
  - Knowledge of databases & SQL.  
  - ORMs → simplify DB interactions (but DB fundamentals are important).  

- Daily responsibilities:  
  - Manage user accounts, authentication, authorization.  
  - Ensure secure storage & transfer of sensitive data.  
  - Retrieve, process, and store data.  
  - Maintain server-side APIs & routing.  

- Nature of the work:  
  - Behind-the-scenes functionality.  
  - Broad technology coverage.  
  - Challenging and constantly changing.  

## 4. Teamwork and Squads

- **Team** = group working toward common goal.  
- Members have different skills, experience, talents.  
- Benefits: focus on strengths, expand skill set, creativity, idea sharing.  

- **Good teamwork needs**:  
  - Trust & respect (built over time, with fair contributions).  
  - Clear goals & agreed roles (avoid duplication/missed tasks).  
  - Use strengths effectively.  
  - Celebrate success & analyze problems.  
  - Strong communication (method that works for all).  

- **Team practices in software engineering**:  
  - Kick-off meetings → plan project, assign tasks, agree goals.  
  - Regular meetings (whole team / sub-teams).  
  - Design/code reviews.  
  - Walkthroughs (for team + stakeholders).  
  - Retrospectives → review successes & improvements.  
  - Mentoring (individual or team).  
  - Internal projects (code standards, legacy code, evaluating tools).  

- **Benefits of teamwork**:  
  - Encourages creativity & knowledge sharing.  
  - Better quality code (standards, documentation, fewer bugs).  
  - More maintainable code.  
  - Reduces stress (help available, problem discussions).  
  - Bigger picture awareness → coherent solutions.  

- **Squads (Agile)**:  
  - Small teams (≤10 developers).  
  - Roles:  
    - Squad leader = anchor dev + coach.  
    - Software engineers = implement features & test cases.  
    - UX developers/designers (1–2).  
  - May use **pair programming**.  

## 5. Pair Programming

- **Definition**: 2 developers work together on 1 computer (physically or virtually).  
- Agile technique → continuous discussion, better solutions.  

- **Styles**:  
  - **Driver/Navigator** → Driver = types, Navigator = reviews + guides. Roles swapped often.  
  - **Ping-Pong** → Test-driven dev. One writes failing test, other writes code to pass. Swap roles. Refactor together.  
  - **Strong Style** → Idea must pass through partner’s hands. Senior = Navigator, Junior = Driver. Good for learning.  

- **Benefits**:  
  - Knowledge & skill sharing.  
  - Speeds up onboarding new members.  
  - Builds soft skills (communication, problem-solving).  
  - Fewer bugs/typos (2 sets of eyes).  
  - On-the-fly code reviews.  
  - Multiple ideas → better solutions early.  
  - Higher quality code, less time fixing later.  

- **Challenges**:  
  - Long focus sessions = exhausting.  
  - Scheduling conflicts.  
  - Risk of one dominating → typist/programmer dynamic.  
  - Personality clashes.  
  - Multiple pairs → noisy environment.  

## 6. Introduction to Application Development Tools

- **Purpose**: Tools help take a Cloud App from idea → code → deployed.  

- **Key developer tools**:  
  1. **Version Control**  
     - Tracks changes, who made them, and when.  
     - Resolves conflicts between multiple developers.  
     - Useful even for solo projects → can revert to older versions.  
     - Often tied to a **code repository** (e.g., Git, GitHub).  
     - Features: branching, merging, history tracking.  

  2. **Libraries**  
     - Collections of reusable code for specific tasks.  
     - Example: carousel code, email validation, jQuery, Apache Commons Proper.  
     - Benefits: saves time, easy integration, call methods as needed.  
     - Control remains with the developer.  

  3. **Frameworks**  
     - Skeletons/scaffolds for building applications.  
     - Define architecture, program flow, and subroutine calls.  
     - Less flexible than libraries → **inversion of control** (framework calls your code).  
     - Opinionated frameworks enforce workflow and standards.  
     - Often include built-in libraries.  
     - Examples: AngularJS, Vue.js, Django.  
     - Must choose early in development → cannot add mid-project.  

- **Analogy**:  
  - Framework = house frame, your code = bricks, plasterboard, finishing touches.  
  - Libraries = specific tools/materials you use on the house.  

- **Summary**:  
  - **Version control** → track and manage changes.  
  - **Libraries** → reusable code for features/tasks.  
  - **Frameworks** → structure, workflow, and standardization.  

## 7. More Application Development Tools

- **Purpose**: Tools to help build, test, and deploy apps efficiently.  

- **CI/CD (Continuous Integration / Continuous Delivery)**  
  - **Continuous Integration (CI)**: integrate new code frequently, test automatically.  
  - **Continuous Delivery / Deployment (CD)**: automatically deploy code to staging or production after CI.  
  - Ensures reliable, frequent updates and smooth teamwork.  

- **Build Tools**  
  - Transform source code → binaries/installable apps.  
  - Organize code, manage dependencies, set compile flags.  
  - Automate tasks like: downloading dependencies, compiling, packaging, testing, deploying.  
  - **Types**:  
    1. **Build-automation utilities** → compile/link code, generate executables.  
    2. **Build-automation servers** → run build utilities on schedule or trigger.  
  - **Examples**: Webpack, Babel, WebAssembly.  

- **Packages**  
  - Archive files containing app code, installation instructions, metadata, dependencies.  
  - Simplifies installation and distribution.  

- **Package Managers**  
  - Automate installation, updates, removal, and dependency management.  
  - Verify integrity via checksums and certificates.  
  - **Platform examples**:  
    - Linux → DPKG, RPM  
    - Windows → Chocolatey  
    - MacOS → Homebrew, MacPorts  
    - Android → Package Manager  
  - **Language-specific examples**:  
    - Node.js → npm  
    - Java → Gradle, Maven  
    - Ruby → RubyGems  
    - Python → Pip, Conda  

- **Summary**:  
  - CI/CD → reliable, frequent integration and deployment  
  - Build Tools → automate compilation and packaging  
  - Packages → bundle app and metadata  
  - Package Managers → install, update, manage dependencies  


## 8. Introduction to Software Stacks

- **Definition**:  
  A **software stack** = combination of technologies (software + programming languages) used to build applications (web, mobile, etc.).  
  - Higher layers → user tasks/services  
  - Lower layers → hardware interaction  

- **Components**:  
  - **Front-end**: languages, frameworks, UI tools  
  - **Back-end**: languages, frameworks, servers, OS, messaging apps, databases  

- **Software stack vs. Technology stack**:  
  - *Software stack*: software + programming tools only  
  - *Technology stack*: broader → includes hardware, VMs, containers, load balancers, etc.  

- **Typical layers**:  
  1. Presentation layer  
  2. Business logic layer  
  3. Data layer  
  (More complex stacks may include: virtualization, orchestration, networking, security, runtime environments, etc.)  

- **Sources**: Internal, third-party, or cloud providers  
- **Flexibility**: No fixed definition → only requirement is to support app development/deployment  


### Examples of Software Stacks

- **Python-Django** → Python + Django (open source, large-scale, fast web apps)  
- **Ruby on Rails** → Ruby + Rails (good with JSON/XML, HTML, CSS, JS)  
- **ASP.NET stack** → ASP.NET MVC + IIS + SQL Server + Azure  


### Popular Named Stacks

- **LAMP**: Linux + Apache + MySQL + PHP  
  - Oldest, widely used, open source  
  - Easy to swap parts (e.g., PostgreSQL → LAPP, Python → replace PHP)  
- **MEAN**: MongoDB + Express.js + Angular.js + Node.js  
  - All JavaScript → one language throughout  
  - Free, open source, lots of reusable modules (Node.js)  
  - Weakness: not ideal for large-scale apps; MongoDB less powerful than relational DBs  
- **MERN**: MongoDB + Express.js + React + Node.js  
  - Variation of MEAN, React for front-end (high performance, flexible)  
- **MEVN**: MongoDB + Express.js + Vue.js + Node.js  
  - Vue.js = lightweight, better performance, but fewer libraries vs Angular  


### Advantages & Disadvantages

- **MEAN**  
  - ✅ All JS (single language), free, fast dev, reusable modules  
  - ❌ Limited for large apps, Express.js restricts reuse, MongoDB lacks relational features  

- **MEVN**  
  - ✅ Similar to MEAN, Vue.js = lightweight, faster UI  
  - ❌ Vue is newer → fewer libraries  

- **LAMP**  
  - ✅ Oldest → large community, reusable solutions, relational DB (MySQL)  
  - ❌ Tied to Linux → less flexible, mixed languages (PHP/Python/Perl + JS) harder for devs, poor for unstructured data  


### Summary

- Software stacks = combinations of technologies for app dev.  
- Range from simple 3-layer → multi-layer systems.  
- Many stacks exist, each with trade-offs.  
- **MEAN/MEVN** → one language (JavaScript), open source, platform agnostic.  
- **LAMP** → strong with relational DBs, older, but less flexible.  

# Module 3 - Basics of Programming

## 1. Interpreted and Compiled Programming Languages

### What are Programming Languages?
- Programming languages help us tell computers what to do.
- Computers use **machine code** (binary: 0s and 1s), not human language.
- To make it easier, developers use **human-readable programming languages**.
- Programming languages are generally categorized as:
  - **Interpreted Languages**
  - **Compiled Languages**

### Interpreted Programming Languages
- Also called **scripting languages**.
- Code is executed by an **interpreter** (software or built-in browser tool).
- Interpreter translates human-readable source code into machine code **at runtime**.
- Often used for repetitive tasks and cross-platform scripts.

#### Characteristics
- Require an interpreter.
- Usually slower than compiled languages.
- Easier to learn, write, and modify.
- Good for quick automation or lightweight programs.

#### Examples
- **JavaScript** → runs in web browsers.
- **Python** → popular, easy to learn, widely used.
- **Lua** → lightweight, often used for game scripting.

### Compiled Programming Languages
- Source code is **compiled** into an **executable file** (.exe, .app, etc.).
- Compiler translates the entire program into machine code **before execution**.
- Programs are typically larger and handle more complex tasks.
- Run faster and repeatedly without needing the source code each time.

#### Characteristics
- Produce standalone executables.
- Better performance.
- Commonly used for operating systems and large applications.

#### Examples
- **C, C++, C#** → used in OS like Windows, macOS, Linux.
- **Java** → platform-independent, used in Android OS (not to be confused with JavaScript).

### Summary
- **Interpreted Languages**: Run scripts through an interpreter (JavaScript, Python, Lua).
- **Compiled Languages**: Create executables via a compiler (C, C++, C#, Java).
- Interpreted → Versatile, cross-platform, easier to learn.  
- Compiled → Faster, efficient, used for complex software like OS and apps.


## 2. Comparing compiled and interpreted programming languages

### Choosing a Programming Language
- Developers choose based on:
  - Their experience and trust in the language
  - What is best for users
  - Efficiency for the task

### Interpreted Programming Languages
- Used for smaller, scripted tasks.
- Source code runs through an **interpreter** (in OS or web browser).
- Also called **script code** or **scripting**.
- Executed **line by line**, like reading a script.
- Each run requires interpreting the source code again.
- Runs on almost any OS with the right interpreter.

#### Example Use Case
- A client wants webpage view stats for last month.
- Use an interpreted language (e.g., Python, JavaScript).
- Script retrieves data and formats it in a table.

#### Examples
- **Python** → general-purpose, case-sensitive, requires Python engine.
- **JavaScript** → scripting in web browsers, case-sensitive, works with HTML.
- **HTML** → markup language, mostly case-insensitive, formats webpages.

### Compiled Programming Languages
- Used for larger, more complex programs.
- Source code is compiled into an **executable file**.
- Installed on the device, runs faster once compiled.
- More difficult to learn but efficient for big tasks.

#### Example Use Case
- A client wants a spreadsheet program to manage data.
- Use a compiled language (e.g., C).
- Example: Microsoft Excel built with C.

#### Examples
- **C** → base for Windows and other OS, case-sensitive, fast execution, less memory use.
- **C++ / C#** → variations of C, also case-sensitive.
- **Java** → compiled, object-oriented, requires JVM, cross-platform (Windows, macOS, Linux), used in Android OS.

### Key Differences
- **Interpreted Languages**
  - Run through an interpreter
  - Easier to learn
  - Cross-platform (with interpreter)
  - Better for websites and repeated small processes
- **Compiled Languages**
  - Compiled into executables
  - Faster execution
  - Harder to learn
  - Better for large, complex programs like operating systems

### Summary
- **Interpreted** → Python, JavaScript, HTML → smaller, repetitive tasks, scripting, requires interpreter.  
- **Compiled** → C, C++, C#, Java → larger programs, executables, faster, used in OS and applications.

## 3. Query and Assembly Programming Languages

### High-Level vs Low-Level Programming Languages
- **High-level languages**: More sophisticated, closer to human language, easier coding/debugging.  
  - Examples: SQL (query), Pascal (structured), Python (object-oriented).  
- **Low-level languages**: Use symbols to represent machine code.  
  - Examples: Assembly languages such as ARM, MIPS, X86.

### Query Languages
- A **query** is a request for information from a database.
- Query languages are used to send predefined instructions to a database.  
- Also called **database query languages**.

#### Common Query Languages
- **SQL** → most prevalent query language.  
- Others: AQL, CQL, Datalog, DMX.

#### SQL vs NoSQL Databases
- **SQL**: Relational, structured schemas.  
- **NoSQL**: Non-relational, dynamic schemas for unstructured data.

#### CRUD Operations
- CRUD = **Create, Read, Update, Delete**.  
- SQL statements used for:
  - **Select queries** → request data.
  - **Action queries** → manipulate data (CREATE, INSERT, UPDATE, DELETE).
- Also used for administrative tasks (e.g., create users, modify permissions).

### Assembly Languages
- Categorized as **low-level programming languages**.
- Represent 0s and 1s of machine code using symbols.
- Each CPU architecture typically has its own assembly language (e.g., ARM, MIPS, X86).
- Translated with an **assembler** (not compiler/interpreter).
- One assembly statement → one machine code instruction.

#### Syntax
- Format: **Instruction/Mnemonic + Operands (optional) + Comments (optional)**.
- Mnemonics (opcodes):  
  - INP → Input  
  - OUT → Output  
  - LDA → Load  
  - STA → Store  
  - ADD → Add

### Key Takeaways
- **High-level languages**: Query (SQL), structured (Pascal), object-oriented (Python).  
- **Low-level languages**: Assembly.  
- **Query languages**: Request or manipulate database data. SQL is most common.  
- **Assembly languages**: Tied to processor architecture, use mnemonics, translated by assembler, one-to-one with machine code.


## 4. Understanding Code Organization Methods

### Why Code Organization Matters
- Makes code easier to **read, maintain, and configure**  
- Reduces bugs and errors across a project’s lifecycle  
- Provides a **consistent and logical format** for coding  
- Well-planned design = **cleaner, more reliable code**  

### Two Main Methods
- **Flowcharts** → pictorial representation of an algorithm  
- **Pseudocode** → high-level text description of an algorithm  

### Flowcharts
- Show steps as **boxes/shapes + arrows** for order  
- Good for **small concepts & early project stages**  
- Easy communication and visualization  

#### Common Symbols
- Start/End → Capsule  
- Process → Rectangle  
- Decision → Diamond  
- Data/Input/Output → Parallelogram  
- Connectors → Arrows  

#### Example: Add Two Numbers
1. Start (capsule)  
2. Input n1, n2 (parallelogram)  
3. Sum = n1 + n2 (rectangle)  
4. Print Sum (parallelogram)  
5. End (capsule)  

#### Flowchart Software
- Microsoft Visio  
- Lucidchart  
- Draw.io  
- DrawAnywhere  

### Pseudocode
- **Informal programming description** (no strict syntax)  
- Used to outline logic before coding  
- Easy for both **programmers & non-programmers** to understand  
- Provides a **bridge between design & actual code**  

#### Example
- Input number  
- If number % 2 = 0 → Print "Even"  
- Else → Print "Odd"  

### Advantages of Pseudocode
- Focuses on **logic, not syntax**  
- Easier to **modify & review** than real code  
- Language-independent → shareable across dev teams  
- Readable by non-programmers  
- Typically **shorter than flowcharts** (less than one page)  

### Summary
- Organized code = **cleaner, more scalable, reliable**  
- Two main methods: **Flowcharts & Pseudocode**  
- Flowchart → pictorial steps with shapes/arrows  
- Pseudocode → plain-language steps, easier for coding phase  

## 5. OOP vs. Procedural Programming

### Compiled vs. Interpreted Languages
- For most developers, the choice doesn’t matter much — often comes down to **personal preference** and **speed of development**.  
- **Compiled languages**:  
  - Provide more guarantees for deployment.  
  - Offer small performance benefits when compiling ahead of time.  
  - Compiler enforces stricter error checking (cannot avoid compiler errors).  
- **Interpreted languages**:  
  - Offer **more flexibility** and runtime possibilities.  
  - Enable creative coding approaches.  
  - More tolerant of runtime experimentation but carry risk of buggy code in production.  
- Ultimately, the choice depends on the **environment** and **risk tolerance** of the project.  

### Object-Oriented Programming (OOP) vs. Procedural Programming
- **Object-Oriented Programming (OOP)**  
  - Anything can be modeled as an **object**.  
  - Provides **hierarchies** and **patterns** for structure.  
  - Easier to keep designs organized and track interactions between objects.  
  - Risk: can lead to **over-structuring** and lots of boilerplate code.  
  - Good for mapping **real-world models** (e.g., Library → Books → Checkout).  

- **Procedural Programming**  
  - Feels more **mathematical** and **engineering-like**.  
  - Focuses on pure functions, logic, and step-by-step problem solving.  
  - Appeals to developers who prefer a direct, mechanical style of coding.  

### Key Insight
- Both OOP and procedural programming have **strengths and weaknesses**.  
- OOP = good for real-world abstractions and scalable designs.  
- Procedural = good for straightforward, mathematical, or low-structure tasks.  
- Developers should try both and find a **balance** between flexibility and structure, depending on the project.  


## 6. Branching and Looping Programming Logic

### Key Concepts
- Two major types of programming logic: **Branching** and **Looping**.  
- Both rely on **Boolean expressions** (true/false) and **variables** (values that can change depending on conditions).  
- Boolean logic allows programs to make decisions and control the flow of execution.  

### Branching Logic
- Branching = program **chooses between different code paths** depending on conditions.  
- Each possible path = a “branch.”  
- Branching constructs:  
  - **if** → executes code if condition is TRUE.  
  - **if-then-else** → executes one block if TRUE, another if FALSE.  
  - **switch** → selects a code block based on variable/expression value.  
  - **GoTo** → jumps to another line of code (less common, often discouraged).  

### Looping Logic
- Loop = sequence of instructions that **repeats until a condition is met**.  
- Used to perform repeated tasks like processing data.  
- Three main loop types:  
  - **While loop** → condition checked *before* executing loop body.  
  - **For loop** → initializes counter, checks condition each time, increments/decrements. Stops when condition is FALSE.  
  - **Do-while loop** → condition checked *after* executing loop body (runs at least once).  

### Summary
- **Branching** = deciding **what action** to take.  
- **Looping** = deciding **how many times** to perform an action.  
- Both use **Boolean logic** and **variables** to control execution.

## 2. Software Design and Modeling

### Learning Objectives
After studying this, you will be able to:

- Discuss the purpose of **interaction diagrams** and **state transition diagrams**  

### Software Design and Modeling Overview
- **Software Design** = Process of documenting **structural components** and **behavioral attributes** before development.  
- A key activity is **modeling**, which uses visual/diagrammatic representations to:  
  - Show the bigger solution and its sub-components  
  - Illustrate interactions between them  
- Can be done via **flowcharts** or standardized **UML diagrams**  

### Structured Design
- Breaks a software problem into **well-organized modules and sub-modules**  
- **Principles:**  
  - **Cohesion** → functionally related elements are grouped together  
  - **Coupling** → degree of communication between modules  
    - **Loose coupling** = weak associations, changes in one module have minimal impact on others  
- Common in **service-oriented** and **microservices architectures**  

#### Example: Billing System
- Main module: `Billing`  
- Sub-modules:  
  - `Insurance Verification`  
  - `Submit Claim`  
  - `Output Total`  
- Arrows represent **data flow** between modules  

### Behavioral Models
- Describe **what the system does** (not how it does it)  
- Communicate overall system behavior using UML diagrams  

#### UML (Unified Modeling Language)
- Standardized modeling language (language-agnostic)  
- Two main categories of diagrams:  
  - **Structural** → show components and their organization  
  - **Behavioral** → show interactions and behavior over time  
- **Advantages of UML:**  
  - Plan features **before coding** → saves time & money  
  - Helps **new developers** or team members onboard quickly  
  - Facilitates communication between **technical & non-technical audiences**  
  - Provides a **visual map** for navigating source code  

### Key UML Behavioral Diagrams

#### State Transition Diagram
- Shows **states** and **events** that cause transitions  
- Example: Patient visiting a clinic  
  - States: `Waiting`, `Testing`, `With Doctor`  
  - Transitions: Events like "appointment scheduled" or "test completed"  

#### Interaction Diagram
- Models **dynamic behavior** and communication between objects  
- **Sequence diagram** (a type of interaction diagram):  
  - Displays object communication **with respect to time**  
  - Example: Patient booking an appointment via online portal  

### Comparison: Structured Design vs Behavioral Models
| Aspect              | Structured Design                          | Behavioral Models                       |
|---------------------|---------------------------------------------|-----------------------------------------|
| Focus               | **Organization** of system into modules     | **Behavior** of system over time         |
| Key Principles      | Cohesion, Loose Coupling                    | States, Events, Object Interactions      |
| Example Diagram     | Module hierarchy (Billing system example)   | State Transition Diagram, Interaction Diagram |

### Summary
- **Structured Design** → breaks problems into modules; emphasizes cohesion & loose coupling  
- **Behavioral Models** → describe what the system does, not how  
- **UML** → standard, language-agnostic way to represent architecture, design, and implementation  
- **State Transition Diagram** → behavioral model showing states and transitions  
- **Interaction Diagram** → behavioral model showing communication between objects over time  


## 3. Object-Oriented Analysis and Design

### Definition  
Object-Oriented Analysis and Design (OOAD) is an approach for analyzing and designing a software system when the system will use object-oriented programming languages such as Java, C++, or Python. It focuses on breaking down a system into **objects** that contain both **data** and **behaviors**.

### Objects  
- Represent entities with attributes (data) and methods (behaviors).  
- Example: A `Patient` object with attributes like `LastName` and methods like `CancelAppointment()`.  

### Classes  
- A **class** is a **blueprint or template** for objects.  
- Objects (instances) are created from classes through **instantiation**.  
- Classes contain generic **attributes** (properties and methods) that are assigned specific values when instantiated.  
- Example: `Patient` class → `Naya Patel` is an instance.  

### Purpose of OOAD  
- Helps organize a system into interacting objects.  
- Enables multiple developers to work on different aspects of the application simultaneously.  
- Makes systems modular, reusable, and easier to maintain.  

### UML Diagrams in OOAD  
- **Behavioral UML diagrams**: Show actions and interactions of objects.  
- **Structural UML diagrams (Class Diagrams)**: Show classes, attributes, methods, and relationships.  

### Class Diagram  
- Each box represents a **class** with attributes (properties) and methods (actions).  
- Shows **relationships** between classes.  
- **Inheritance**: Subclasses inherit attributes and methods from parent classes, while adding their own.  
  - Example: `Nurse`, `Doctor`, and `Technician` are subclasses of `MedicalPersonnel`.  
  - `Specialist` is a subclass of `Doctor`.  
  - This means a Specialist can do anything a Doctor can, and a Doctor can do anything MedicalPersonnel can.  

### Key Takeaways  
- OOAD is the process of planning software based on interacting objects.  
- Objects contain **data** and **behaviors**.  
- **Classes** are blueprints for objects.  
- **Class diagrams** are UML diagrams that represent structure and relationships in object-oriented design.  

## 4. The Importance of Design and Software Architecture

### Definition  
Design and architecture are crucial aspects of software engineering. They ensure that systems are prepared to handle requirements, environments, and interactions effectively. Without proper planning, code may be written inefficiently, leading to wasted time and rework.  

### Architecture as Orchestration  
- Architecture can be compared to orchestration in music.  
- Even if individual components (instruments) are well-designed, without coordination, the result can be chaotic.  
- The bigger picture and system-level synchronization are essential.  

### Sustainability and Planning  
- Architecture helps ensure that the system fits into the **larger ecosystem**.  
- Writing code without design may lead to wasted effort if the solution is not sustainable.  
- Good architecture ensures that code persists, scales, and gets used effectively.  

### Scalability and Global Availability  
- A design may work well in a **local context** but fail at a **global scale**.  
- Architecture ensures systems are built to handle different usage levels, from a single user to millions.  
- Considerations include:  
  - Data sources and flows.  
  - How data is passed and shared across modules/services.  
  - How to optimize network hops to avoid timeouts and performance issues.  

### Microservices and Data Handling  
- In microservice architectures, **data loading and sharing** become critical.  
- Distributed systems require careful planning of **communication, access, and latency management**.  
- Proper design avoids “churny code” caused by undefined responsibilities.  

### Identity and Access Management  
- Architecture must define **who is using a service** and **what permissions they have**.  
- Questions to answer:  
  - How are users authenticated?  
  - How is account management handled?  
  - How do services identify and communicate with each other securely?  

### Core Architectural Questions  
When designing a system, three big questions should always be addressed:  
1. **What** – What components are needed?  
2. **Where** – Where will they reside (server, cloud, distributed nodes)?  
3. **Scope** – What responsibilities does each component have?  

### Long-Term Thinking  
- Architecture is about **planning for the future** (5–10 years ahead).  
- Avoid frequent re-architecture and instead aim for **sustainable design**.  
- Systems should evolve incrementally, similar to maintaining and repairing buildings rather than rebuilding entirely.  

### Key Takeaways  
- Architecture ensures sustainability, scalability, and proper coordination.  
- It reduces wasted effort by anticipating needs early.  
- Good design avoids churn, improves communication, and ensures system longevity.  
- Sustainable systems require **incremental evolution**, not constant rework.  


## 5. Approaches to Application Architecture

### Components  
- A **component** is an individual unit of encapsulated functionality that works with other components to form an application.  
- **Six characteristics of components:**  
  1. **Reusable** – Designed for use in multiple applications.  
  2. **Replaceable** – Easily swapped with another component.  
  3. **Independent** – Minimal dependencies on other components.  
  4. **Extensible** – Behavior can be added without changing others.  
  5. **Encapsulated** – Internal state is hidden; data and methods are bundled.  
  6. **Non-context specific** – Works in different environments; internal state is set externally.  

**Examples of components:**  
- API packaged for reuse across multiple systems.  
- Data access object (DAO) that allows switching databases without the application knowing.  
- Controller that manages the flow of data between components.  

### Component-Based Architecture  
- Focuses on decomposition into **logical independent components**.  
- Provides a **higher level of abstraction** than object-oriented designs.  
- Defines, composes, and implements loosely coupled independent components.  

### Services  
- **Service = unit of functionality** like a component, but with differences:  
  - Designed to be **deployed independently**.  
  - **Reused by multiple systems**.  
  - Focuses on solving a **business need**.  
  - **Single unique instance**, always running, accessed by multiple clients.  

**Examples of services:**  
- Checking a customer’s credit.  
- Calculating monthly loan payments.  
- Processing a mortgage application.  

**Relationship:**  
- **Objects → Components → Services** (layered architecture).  
- A **service is a type of component**, but designed for broader reuse and deployment.  

### Service-Oriented Architecture (SOA)  
- Services are **loosely coupled** and interact via communication protocols (e.g., HTTP).  
- Supports **distributed systems** where services deliver functionality to other applications.  

### Distributed Systems  
- A system with **multiple services on different machines** that coordinate via messages.  
- Appears to end-users as a **single coherent system**.  

**Key characteristics:**  
- **Resource sharing** – hardware, software, and data.  
- **Fault-tolerant** – continues running despite node/service failures.  
- **Dynamic** – system may change during execution without interruption.  
- **Concurrent execution** – multiple activities reduce latency, increase throughput.  
- **Scalable** – supports growing numbers of users.  
- **Heterogeneous** – supports different hardware, OS, and languages.  

**Nodes in distributed systems:**  
- Any device that can recognize, process, and transmit data to others.  
- Nodes run one or more services within the SOA.  

**Architectural styles used:**  
- Client-server.  
- Three-tier.  
- Peer-to-peer.  
- Microservices.  

### Key Takeaways  
- Components must be reusable, independent, replaceable, extensible, encapsulated, and non-context specific.  
- **Component-based architecture** breaks down systems into logical independent components.  
- **Services** are made of components and deployed independently for reuse.  
- **SOA** enables loosely coupled services to interact over a network.  
- **Distributed systems** consist of multiple nodes/services, appear as one system, and are scalable, fault-tolerant, and concurrent.  

## 6. Architectural Patterns in Software

### Overview  
- **Architectural pattern**: A repeatable solution to a software architecture problem.  
- Patterns highlight common internal elements and structures of a system.  
- Different patterns may share related characteristics.  
- In this video, we cover: **2-tier, 3-tier, peer-to-peer, event-driven, and microservices**.  
- Other patterns (not covered): model-view-controller (MVC), message-broker, blackboard, pipe-filter, controller-responder.  

### 2-Tier Architecture (Client-Server)  
- **Definition**: Server hosts, delivers, and manages most resources/services while client provides the interface.  
- Clients request services/data from server over a network.  
- Multiple clients usually connect to a server.  

**Examples:**  
- Text messaging apps (client sends message to server → server delivers to another client).  
- Database clients connecting to database servers.  

### 3-Tier Architecture (N-Tier)  
- **Most common software architecture**.  
- Composed of **horizontal tiers** functioning as one unit.  
- A tier only communicates with the one above or below it.  
- Related components are grouped in the same tier.  
- **Change in one tier does not affect others**.  

**Three tiers:**  
1. **Presentation tier** – User interface.  
2. **Application tier (middle)** – Processes business logic.  
3. **Data tier** – Stores and manages data.  

**Examples:**  
- Web apps → UI via web server, business logic via app server, data via database server.  

### Peer-to-Peer (P2P)  
- **Decentralized network of nodes** acting as both clients and servers.  
- Workload is partitioned across peers.  
- Peers share resources (processing power, storage, bandwidth).  
- Contrast: In client-server, clients consume and servers provide.  

**Examples:**  
- File sharing, instant messaging, collaboration, high-performance computing.  
- Cryptocurrencies like **Bitcoin, Ethereum**.  

### Event-Driven Architecture  
- **Event** = action that changes state (e.g., mouse click, program trigger).  
- **Producers** listen/react to triggers and publish events.  
- **Router** pushes events to the right consumer.  
- **Consumers** process event notifications.  
- Components are **loosely coupled**, making this pattern good for **distributed systems**.  

**Example:**  
- Ride-sharing apps (Uber, Lyft): customer request = event routed to a consumer (driver).  

### Microservices Architecture  
- Application divided into **modular services**.  
- Each service = self-contained functionality, reusable, independently deployable.  
- Communication handled via **APIs**.  
- **API Gateway** routes requests.  
- **Orchestration** manages communication between services.  

**Examples:**  
- Social media platforms: account management, friend requests, ads, and content display handled by separate microservices.  

### Combining Patterns  
- **Patterns are not always mutually exclusive.**  
- Some combinations:  
  - 3-tier + Microservices.  
  - Peer-to-peer + Event-driven.  
- Some cannot be combined:  
  - P2P ≠ 2-tier (P2P nodes = client + server, 2-tier separates them).  

### Key Takeaways  
- **Architectural pattern** = repeatable solution to a design problem.  
- **2-tier** = client + server (e.g., text messaging, DB apps).  
- **3-tier** = presentation, application, data (e.g., web apps).  
- **Peer-to-peer** = decentralized nodes (e.g., crypto).  
- **Event-driven** = producers + consumers (e.g., ride-sharing apps).  
- **Microservices** = modular services, API-driven (e.g., social media).  
- **Multiple patterns can be combined**, but not all are compatible.  


## 7. Application Deployment Environments

### Overview
- An **application environment** is the combination of hardware and software resources required to run an application.  
- Components include:  
  - Application code or binaries for various modules.  
  - Software stack: modules, libraries, third-party apps, middleware.  
  - Operating system, networking components, and infrastructure.  
  - Physical or virtual hardware: CPU, memory, storage.  
- Environment types vary depending on the **stage in the lifecycle**.  

### Pre-Production Environments
- **Purpose**: Platforms where the application is prepared for production.  
- Common types: **Development, QA, Staging**.  

**Development Environment**  
- Platform where application is actively coded.  
- Often just the developer’s workstation.  

**QA Environment (Testing)**  
- Allows QA team to test the application’s components.  

**Staging Environment**  
- Closely replicates the production environment.  
- Not intended for general users.  

### Production Environment
- Intended for all users.  
- Includes **entire solution stack**: hardware + software + additional infrastructure components.  
- Must handle **application load** for potentially thousands or millions of users.  
- Consider **non-functional requirements**: security, reliability, scalability.  

### Deployment Options

**On-Premises Deployment**  
- System and infrastructure reside in-house, behind a firewall.  
- Organization responsible for hardware, infrastructure, and maintenance.  
- Advantage: greater control and security.  
- Disadvantage: usually more expensive than cloud deployment.  

**Cloud Deployment Models**  

**Public Cloud**  
- Uses cloud provider’s hardware and infrastructure over the internet.  
- Shared with other organizations.  
- Examples: AWS, Microsoft Azure, Google Cloud, IBM Cloud.  
- Advantage: scalable and cost-effective.  

**Private Cloud**  
- Cloud infrastructure dedicated to a single organization.  
- Can be on-premises or managed by a service provider.  
- Advantage: increased security and flexibility.  

**Hybrid Cloud**  
- Combination of public and private cloud working together.  
- Optimizes cost, security, scalability, and flexibility.  

### Key Takeaways
- **Application environments**: development, QA/testing, staging, production.  
- **Production environment** considerations: load, security, reliability, scalability.  
- **Deployment options**: on-premises, public cloud, private cloud, hybrid cloud.  


## 8. Production Deployment Components

### Overview
- Purpose: Describe components commonly required for deployment in a production environment.  
- Key components: firewall, load balancer, web servers, application servers, proxy servers, database servers.  

### N-Tier Architecture
- **Presentation Tier**: Front-end client applications.  
- **Web Tier**:  
  - Contains a web load balancer.  
  - Distributes incoming traffic to several web servers.  
- **Application Server Tier**:  
  - Contains an application load balancer or proxy server.  
  - Routes traffic to different application servers.  
- **Data Tier**:  
  - Contains the database server.  
  - Often includes a high-availability replica for reliability.  
- Note: Not all components are necessary for every deployment.  

### Firewall
- Security device that monitors traffic between networks.  
- Permits or blocks data based on security rules.  
- Acts as a barrier against viruses, malware, and hackers.  

### Load Balancer
- Distributes network traffic efficiently among multiple servers (server farm).  
- Prevents server traffic overload.  
- Ensures high availability and responsiveness.  
- Manages concurrent client requests.  

### Web Server
- Software or machine that provides services, resources, or applications to clients.  
- Delivers content such as web pages, files, images, and videos.  
- Primarily responds to HTTP requests from web browsers.  

### Application Server
- Runs business logic and provides the application to clients.  
- Enables interaction between the end-user and server-side application code.  
- Executes business logic for creating, storing, and updating data.  

### Proxy Server
- Intermediate server between two tiers.  
- Handles requests between tiers.  
- Purposes: load balancing, optimization, caching, firewall, privacy, encryption, malware scanning.  
- Improves efficiency, privacy, and security of data flow.  

### Database Server
- Stores and controls flow of data via a **Database Management System (DBMS)**.  
- DBMS connects database to users or other programs.  
- Database server enables retrieval and manipulation of data for applications.  

### Key Takeaways
- Common production components: firewall, load balancer, web/app servers, proxy servers, database servers.  
- **Firewall**: monitors network traffic.  
- **Load balancer**: distributes traffic among servers.  
- **Web server**: delivers content to clients.  
- **Application server**: executes business logic.  
- **Database server**: manages and stores application data.  



## 9. Deployment Architecture

### Overview
- Purpose: Discuss key aspects of software deployment and architectural decisions.  
- Considerations: scale, data flow, real-time access, logging, privacy, system availability, and modular code design.  

### Key Design Principles
- **Scale**: Determine how many users your system will support and the expected data volume.  
- **Data Access**: Assess how real-time data access needs to be.  
- **Logging**: Define logging requirements for both internal and external data analysis.  
- **Privacy**: Ensure proper handling and anonymization of data where needed.  

### Infrastructure Decisions
- **Serverless vs. Hosted vs. Self-hosted**: Decide whether to use serverless platforms, hosted backends, or host your own infrastructure.  
- **System SLOs (Service Level Objectives)**: Define what constitutes a healthy and well-running system.  
- **Monitoring**: Set up monitoring to ensure objectives are met and have mitigation plans if they fall short.  

### Code Structure
- Use **microservices** and modularized code to avoid bloated codebases.  
- Modularization helps developers move quickly and deploy faster.  

### Testing and Deployment Practices
- **Testing is fundamental**: Focus on test-driven development (TDD) as a core practice.  
- **Canarying**: Roll out new code in small increments to test for issues before full deployment.  
- **Release and Rollback Strategy**: Plan how quickly new code can be released or rolled back if needed.  

### Key Takeaways
- Consider scale, logging, privacy, and SLOs before deployment.  
- Modular code and microservices enable faster and safer deployment.  
- Testing, TDD, and canarying are critical to ensuring stable deployments.

## 10. Code of Ethics

### Overview
- The **Software Engineering Code of Ethics** was developed by the **IEEE-CS** (Institute of Electrical and Electronics Engineers Computer Society) and the **ACM** (Association for Computing Machinery).  
- Purpose: to hold software engineers accountable and maintain the profession’s status as beneficial and respected.  
- Applies to everyone in or related to the field: engineers, mentors, instructors, managers, students, and policymakers.  
- Covers the full lifecycle: specification, analysis, design, development, testing, and maintenance of software.  
- Consists of **eight principles** dedicated to serving the **public interest**.

### Eight Principles

#### 1. Public
- Act primarily to benefit the public good.  
- Accept responsibility for work with respect to safety, fairness, accessibility, and integrity.  

#### 2. Client and Employer
- Act in the best interests of both clients and employers.  
- Be honest and forthright about unethical or illegal activities (e.g., plagiarism).  
- Seek consent where appropriate and honor confidentiality.  

#### 3. Product
- Strive for quality in the software product while balancing cost and timelines.  

#### 4. Judgment
- Maintain integrity, independence, and objectivity.  
- Avoid inappropriate financial activities (e.g., bribery, double billing).  
- Do not accept duties that create conflicts of interest.  

#### 5. Management
- Managers and leaders should model ethical behavior.  
- Minimize risks, ensure security procedures, and set realistic expectations.  
- Provide just compensation and procure intellectual property rights when appropriate.  

#### 6. Profession
- Protect and enhance the reputation of the profession.  
- Act with integrity, not at the expense of others.  
- Express concerns over violations of the code.  

#### 7. Colleagues
- Treat peers with fairness and respect.  
- Encourage compliance with the code of ethics.  
- Do not take credit for others’ work.  

#### 8. Self
- Commit to lifelong learning and professional development.  
- Strive to create high-quality software.  
- Conduct oneself professionally.  

### Key Takeaways
- The code is a **supplemental guide**, not a replacement for common sense or conscientious decision-making.  
- It ensures software engineers act ethically in **analysis, design, development, testing, and maintenance**.  
- Eight principles: **Public, Client/Employer, Product, Judgment, Management, Profession, Colleagues, Self**.
